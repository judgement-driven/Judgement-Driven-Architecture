# JDA v1.8 Update Memo

本ドキュメントは、JDA v1.7公開後の実装・運用を通じて得られた知見を記録する。

ここに記載する内容は、v1.8で採用することを前提としたものではなく、
今後の検討候補を整理するためのメモである。

---

## 1. 業務設計とシステム設計の分離

### 背景

BJ04（制作進行）の設計を進める中で、JDAはシステム設計手法ではなく、
業務における判断構造を設計する手法であることがより明確になった。

従来の要件定義では、画面・データ項目・画面遷移から設計が始まることが多い。

一方JDAでは、

```text
BJ
↓
JP
↓
State
```

という業務モデルを先に設計する。

その後、

- UI
- API
- DB
- 通知
- ファイル管理

などのシステム設計は、この業務モデルを前提として構築する。

---

### AI時代との親和性

AIを利用した開発では、UIやシステム構成を高速にプロトタイピングできる。

そのため、

- 画面
- レイアウト
- 操作方法
- 通知方法

などは利用者と対話しながら繰り返し改善できる。

しかし、

```text
BJ
JP
State
```

という業務モデルは変更しない。

つまり、

**業務モデルを固定し、システムを反復的に改善する**

という開発スタイルが可能になる。

---

### 今後の検討事項

この考え方をJDA Coreへ正式に取り込むかは、
BJ04以降の実装結果を踏まえて判断する。

実際に、

- JPを変更せずUIのみ改善できたか
- プロトタイピングとJDAが両立したか
- 業務モデルが安定したままシステム改善できたか

を確認した上で、v1.8への採用を検討する。

## 2. Proposalライフサイクル

### 背景

BJ04（制作進行）の設計を進める中で、Proposalの位置付けについて新たな気付きが得られた。

BJ01ではProposalは営業活動の成果として生成される実行単位として扱っていたが、BJ04では制作進行の対象としてそのまま利用されることになる。

さらに、BJ05（納品）、BJ06（請求）、BJ07（入金）まで考えると、Proposalは営業だけでなく業務全体を通して利用される可能性が見えてきた。

---

### 仮説

```text
Company
│
└── Proposal
        │
        ├── BJ01で生成される
        ├── BJ04で制作対象となる
        ├── BJ05で納品対象となる
        ├── BJ06で請求対象となる
        └── BJ07で入金対象となる
```

Proposalは、複数BJを通して利用される業務オブジェクトになる可能性がある。

---

### 検証事項

以下をBJ04〜BJ07の実装を通じて確認する。

- Proposalを複数BJで共通利用できるか
- Proposalを中心に状態遷移を管理できるか
- Proposalが業務ライフサイクルの中心オブジェクトとして機能するか
- Coreで定義しているProposalの説明を拡張する必要があるか

---

### 備考

現時点では実装前の仮説である。

BJ04〜BJ07の実証結果を踏まえ、必要であればCoreへ反映する。
